### 1.3 Match-start flow today (VERIFIED against the actual `NetworkTestScene.unity` serialized data)

1. Editor Play (or a built client) loads `NetworkTestScene`.
2. Every peer's `GameManager.Start()` unconditionally calls `_ = InitializeUnityServicesAsync()` (Unity Services init + anonymous sign-in). `StartSession()` is **not** auto-called: the scene's `GameManager` component has `startSessionOnPlay: 0` (VERIFIED by reading the scene YAML directly) — my original guess that it might auto-run was wrong; confirmed off.
3. However, a **separate, always-active** `SpawnManager` GameObject (VERIFIED present and `m_IsActive: 1` in `NetworkTestScene`, with `autoPositionLocalPlayer: 1`) runs its own unconditional `Start()` → `PositionLocalPlayerAtSpawn()` → `GameObject.Find("Player")`, and teleports whatever is named "Player" to spawn slot 0 — with **no networking awareness at all** (no `IsNetworkSessionActive`/`IsOwner`/`IsServer` check of any kind). This runs on every peer's scene load independently of `GameManager`/`PlayerSpawner`. See the corrected §2 row below — this is live code, not legacy.
4. A user clicks **Host**: `LobbyUI.OnHostButtonPressed()` → `NetworkManagerExt.CreateRelay()` (Unity Relay allocation + join code) → `NetworkManagerExt.StartHost()`. `NetworkSessionManager` (in-scene `NetworkObject`) adds the Host's own roster entry via `NetworkManager.OnClientConnectedCallback`.
5. Another user clicks **Join** with the room code: `NetworkManagerExt.JoinRelay(code)` → `StartClient()`. NGO auto-spawns that client's own `Player.prefab` instance.
6. The Host presses **`[R]`** (a literal keyboard hotkey, read directly in `GameManager.Update()`), which calls `RestartSession()` → `StartSession()` — this is the **only** place `PlayerSpawner.SpawnPlayers()` / the full session-init path actually runs, and the point the networked match state (`NetworkGameState`'s `NetworkVariable`s) is (re)initialized and pushed to clients.
7. Gameplay proceeds: players move (owner-authoritative, replicated via NetworkTransform), interact with doors (own `NetworkVariable` + `Rpc`) and the Reactor console (routed through `NetworkGameState.RequestActivateReactorRpc`), countdown ticks server-side and replicates down.
8. Disconnect handling (Story 3.6): `NetworkSessionManager` removes the roster entry; NGO despawns the leaving player's `NetworkObject` on every machine (`DontDestroyWithOwner = false`); `LobbyUI`/`GameManager.HandleHostDisconnected()` return a Client to a safe "session ended" UI state if the **Host** was the one who disconnected.

**This entire flow assumes the Host is also a player** sitting at the keyboard — see §2. Note the `[R]` keypress is still the sole trigger for `PlayerSpawner`'s real spawn path even though auto-start is off — a dedicated server has no keyboard, so this remains the single highest-priority gap (see §2, first row).

## 4. Unity Relay / Authentication / Services Core dependencies bypassable in server mode

- **`com.unity.services.authentication` 3.8.0** and **`com.unity.services.multiplayer` 2.3.3** (which itself bundles Relay, Lobby-adjacent, QoS, and Wire services as transitive dependencies — VERIFIED from `packages-lock.json`; there is no separate `com.unity.services.relay` package, confirming Relay ships inside `com.unity.services.multiplayer` in this SDK generation) are used exclusively by `GameManager.InitializeUnityServicesAsync()` and `NetworkManagerExt.CreateRelay()/JoinRelay()`.
- Both call sites are reachable from **every** peer today, including what would become the dedicated server build. Both need a server-mode bypass: the server should not sign in anonymously, allocate/join Relay, or depend on Services Core being reachable — it should listen directly on a UTP endpoint and trust a backend-issued join token instead (`ARCHITECTURE_RULES.md` Rule 6).
- Packages themselves do not need to be removed — just unused/compiled-out under a server role (see §6 on Multiplayer Roles, currently disabled).

## 5. What can be reused unchanged

- **`PlayerController`'s owner-gated movement/input.** Every input read and physics-affecting call is already gated behind `IsOwner`, and the server is never an owner of any player object — this pattern already works correctly for a dedicated server with zero changes required. This also matches your SRS's own `BR-03`/`FR-NET-03` (movement is explicitly client-predicted, not server-recomputed).
- **The `NetworkVariable` + `Rpc(SendTo.Server)` pattern** established in `DoorController` and `NetworkGameState` (Host validates range/state server-side, writes the `NetworkVariable`, every peer reacts only via `OnValueChanged`). This is exactly Rule 3's "input up, state down" and should be the template for every future Station/Task.
- **`GameManager.IsHostAuthoritative`** — algebraically already equals `IsServer` on a real dedicated server (see §2). Reusable with zero changes.
- **The `EventChannelSO` pub/sub bridge** (`GameSessionStateEventChannelSO`, `ObjectiveDataEventChannelSO`, `FloatEventChannelSO`) from replicated state to `HUDManager`. This decoupling already means the HUD never needs to change regardless of what drives the underlying state — a strong foundation for later per-client hidden-information filtering.
- **The `ReactorCoreConsole`/`NetworkGameState` bridging pattern** for non-`NetworkBehaviour` interactables (single-inheritance workaround). Reuse for any future Station that extends `InteractableBase`.
- **Story 3.6 disconnect-handling shape** (detect-your-own-disconnect, return to a safe state, clear displayed state) — the specific "Host disconnected" framing won't apply to a dedicated server (the server doesn't "leave"), but the underlying client-side "I lost my connection to the authority, go to a safe state" behavior is exactly what's needed when a dedicated server itself goes down; reusable with a rename/reframe, not a rewrite.
- **`ARCHITECTURE_RULES.md`** itself — already written for the target state (see §0.2). Use as the plan's constitution; no changes needed there.
